Rapport de test : OCR et vision avec un LLM miniature

Campagnes du 17 et du 20 novembre 2026. Mesures reproductibles, contrôles d’interface et limites écrites.

Version testée : 1.0.1 · Dernière mise à jour : 2026-11-20
Objet

La démo analyse une image dans le navigateur avec le modèle de vision Mirage, compilé en WebAssembly. Elle produit un JSON qui contient les objets détectés, le texte reconnu, les relations visuelles et une description de la scène. Ce rapport vérifie trois choses : que l’analyse fonctionne sur trois images de nature différente, que l’interface fait ce qu’elle annonce, et que l’image ne quitte pas le navigateur.

Le rapport décrit aussi ce qui n’a pas été vérifié. Une mesure absente n’est pas une mesure réussie.

Lors du rejeu du 20 novembre, le harnais récupère l’image du contrôle glisser-déposer à l’adresse /exemples/images/..., à la racine du site. Dans l’arborescence du lab, les images vivent sous /demos/ocr-llm-miniature/exemples/. Ce contrôle échoue donc dans ce contexte, alors que l’import par le champ de fichier et l’analyse réussissent. C’est une limite du harnais, pas de la démo. Le second 404 observé est la tentative ./models/mirage.cact, attendue puisque les poids ne sont pas publiés dans le lab.

Publication statique

Un dossier _site a été construit comme le fait le workflow (contenu de wasm-app et images de exemples), puis servi par un serveur statique local, sans modèle local. L’application a téléchargé mirage.cact depuis Hugging Face, puis analysé l’image. Le JSON produit est identique octet pour octet à celui obtenu avec le modèle servi localement, empreinte SHA-256 BD53EB469C6FDA5674FF47E1D45F562D758B51ED23FA4BF9AB474F66CDE13401.

Ce test valide le chemin de publication, pas le déploiement lui-même. Les contrôles de mise en ligne sont décrits plus bas.

Mise en ligne sur lab.adamai.fr

La démo est publiée à l’adresse https://lab.adamai.fr/demos/ocr-llm-miniature/. Son URL canonique pointe sur cette adresse, et non sur l’ancien site de projet GitHub.

Les poids du modèle ne sont pas stockés dans le dépôt du lab : ils sont téléchargés depuis Hugging Face au premier usage, puis mis en cache par le navigateur. Les trois images de la documentation accompagnent la démo, pour que les exemples restent lisibles sans dépendance externe.

Le domaine ne publie qu’un seul fichier robots.txt et un seul sitemap.xml, à la racine. Les fichiers de même nom présents dans une démo sont ignorés par les moteurs de recherche et ne sont pas publiés.

Ce qui n’a pas été vérifié
  • Google Chrome, Firefox et Safari. Chrome n’était pas installé, les deux autres n’ont pas été exécutés.
  • L’inférence en mode serveur avec la CLI Cactus, absente du poste. La route répond, mais l’analyse n’a pas été exécutée.
  • Le comportement sur une connexion lente ou coupée pendant le téléchargement du modèle.
  • L’accessibilité par lecteur d’écran, contrôlée seulement à la main et partiellement.
  • La qualité générale du modèle sur d’autres images que les trois images de référence.
  • La tenue de charge sur des images très grandes.
  • L’extraction fiable de montants ou de champs comptables.

Une extension de sécurité Kaspersky injecte un script dans les pages de test. Cette requête vient de l’antivirus du poste, pas de l’application.

Conclusion

Le mode WebAssembly, l’interface française, l’export JSON et les trois tests de référence fonctionnent et sont reproductibles. Les limites restantes sont documentées et datées.

La démo n’est pas un produit fini : c’est une démonstration mesurée, avec ses angles morts écrits. C’est précisément ce qui la rend utilisable en rendez-vous client.
